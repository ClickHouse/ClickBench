# Ravel

[Ravel](https://github.com/NOFireAI/ravel) is an object-storage-native telemetry
database. Logs, metrics and traces are ingested into immutable objects in
S3-compatible storage, which is the only durable backend: there is no local-disk
storage mode and no local state a restart depends on. ClickBench's `hits` table
is loaded as the logs signal, with each column declared as a typed attribute
column, and queried over SQL.

For this benchmark the object store is a single-node
[s3s-fs](https://github.com/s3s-project/s3s) that `./install` sets up, starts
and provisions on the machine's own disk, so the entry runs like the other
local-disk systems in this repository and needs no cloud account. Run it the
usual way:

```sh
./benchmark.sh
```

## What this entry needs

Nothing from the operator. `./install` downloads a prebuilt s3s-fs for the
host architecture from a release on our fork and verifies it against that
release's `SHA256SUMS` (if the release is unreachable it builds the same
pinned commit with `cargo install --locked`, installing a minimal Rust
toolchain if the machine has none), generates a credential pair into a file
readable by the current user only (`store/credentials.env`), starts s3s-fs on
loopback with its data
directory under `store/data`, creates the bucket, and runs `ravel-cli store
qualify` once, the bucket's one-time conformance check (conditional writes,
read-after-write and list-after-write consistency, listing order). The first
`./start` bootstraps the bucket's `sys/tenancy` marker to the unkeyed
tenant-hash derivation: the server's own default is the keyed derivation,
which refuses to start without a deployment key file, and this benchmark holds
no secret and needs a derivable prefix for `./data-size`.

Credentials reach s3s-fs and Ravel through the environment, never a command
line; `ravel-env.sh` reads them from the generated file. The same file holds
the key the server tokenizes query text with on its audit trail
(`RAVEL_AUDIT_TOKEN_KEY`, generated by `./install` too): a keyed deployment
derives that key, and this entry runs unkeyed, so it supplies one of its own.
The entry opens two loopback ports, the store's and the database's. `./stop`
stops the database only. s3s-fs stays up across the driver's restart cycle and
`./store-start` restarts it if it is ever found down, so the drop of the page
cache before each cold run reaches the store's files the same way it reaches
any local-disk engine's.

### The object store

The store is s3s-fs, the file-system backend of the s3s project, instead of
RustFS, which earlier versions of this entry used. The binary comes from a
release on [our fork](https://github.com/NOFireAI/s3s), built from a pinned
commit and verified against the release's `SHA256SUMS`: the s3s-fs
v0.17.0 release plus two changes offered upstream, one that returns each
object's stored ETag in listings
([s3s-project/s3s#1013](https://github.com/s3s-project/s3s/pull/1013)), which
Ravel's store qualification requires, and one that reads the access and secret
key from the environment instead of the argument list
([s3s-project/s3s#1014](https://github.com/s3s-project/s3s/pull/1014)). Both
are single-node S3 servers over this machine's disk; the difference is what a
ranged read costs. On a single drive RustFS reads a whole 1 MiB erasure block
around every ranged GET (about 1.5 MB of disk per 10 KB range, measured on
c6a.4xlarge), while s3s-fs serves a range with one file read. Ravel's cold
reads are ranged, so on RustFS the cold figures measured the store's read
amplification more than the database; see "What the cold figures measure
here" below.

To run the same scripts against another S3-compatible store, set
`RAVEL_S3_ENDPOINT`, `RAVEL_S3_BUCKET`, `RAVEL_S3_ACCESS_KEY` and
`RAVEL_S3_SECRET_KEY` before `./install`; a non-loopback endpoint skips the
s3s-fs setup. `RAVEL_S3_REGION` defaults to `us-east-1`.

Optional: `RAVEL_TENANT` (default `clickbench`), `RAVEL_SHARDS` (default 4,
must match between `./load` and `./start`), `RAVEL_VERSION` (default the
released version `./install` downloads), `RAVEL_REF` (build that ref from
source instead), `S3S_FS_GIT`, `S3S_FS_RELEASE` and `S3S_FS_REV` (the
repository, the release the s3s-fs binary is downloaded from, and the commit
it is built from when that release is unreachable).

## How the run is configured

`./install` downloads the released `ravel-server` and `ravel-cli` for the host
architecture and verifies them against the release's `SHA256SUMS`; those are the
binaries extracted from the signed container images, so what runs here is what
the published image runs. If the release is unreachable it falls back to
building the pinned ref from source with `--release`.

`./start` passes **one performance flag**: from 30 GB of `MemTotal` up it
turns on the decoded column-block cache with
`--decoded-cache-max-bytes 8000000000`. Below 30 GB the cache stays off, the
server's default. The cache keeps decoded columns between statements, so a
warm statement skips their decode. Its entries are charged to the server's
memory budget, and memory pressure evicts them before a query is refused. The
8 GB cap was chosen on c6a.4xlarge from 4, 8 and 12 GB: at 4 GB the cache
churned and two statements ran slower than without it, and 8 GB came within
0.2 % of 12 GB's warm-run geomean. `RAVEL_DECODED_CACHE_BYTES` overrides it, and
`0` turns it off. Everything else the server resolves at startup: fetch concurrency from the core count, the read caches and
the SQL memory ceilings as shares of one memory budget derived from usable
memory (`MemTotal`, capped by the cgroup memory limit when it runs in a
container, less a fixed reserve), with a fixed segment cap and engine deadline.
Every resolved value and its source is logged on a `performance default
resolved` line in `server.log`; a published result should record those lines,
because they are the configuration the numbers were measured at. On
c6a.4xlarge, with the store on loopback, v0.28.0 resolved the fetch cache to
7.1 GB, the per-query SQL pool to 16.5 GB and fetch concurrency to 32, as
v0.27.0 did.
`./start` also raises the process's open-file
soft limit to the hard limit, since the server has exited with `EMFILE` at
startup under the common default of 1024.

`./load` declares the typed attribute columns and then loads the Parquet file
in 100,000-row batches. Since 0.23.0 a shard merges several batches into one
stored object until its buffer's estimated uncompressed content reaches
`--target-bytes`; at 1,850,000,000 that gives objects of about 25 MB on this
dataset (about 420 objects in all on v0.27.0; a stored object is about 1/74 of the
estimate here). Before 0.23.0 each batch was its own object, about 4 MB. Large
objects are what make a cold scan cheap. The loader holds its batches under
`--load-memory-bytes`, so the load fits the machine. `./load` picks the
pipeline depth, read cursors and that budget from `MemTotal`:

| MemTotal | `--pipeline-depth` | `--read-cursors` | `--load-memory-bytes` |
|---|---|---|---|
| 30 GB and up | 56 | 16 | 14,000,000,000 |
| 15 to 30 GB | 32 | 16 | 6,500,000,000 |
| 7 to 15 GB | 24 | 16 | 3,500,000,000 |
| 3 to 7 GB | 16 | 2 | 1,200,000,000 |
| under 3 GB | 8 | 1 | derived by the loader |

From 30 GB up `./load` also writes larger objects, each one row group:
`--target-bytes 3700000000` and `--group-target-blocks 512` give objects of
about 46 MB and 450,000 rows (223 objects on c6a.4xlarge with v0.27.0), and
each column of an object is one contiguous range. The age trigger there is
`--max-flush-delay 60s`, since a larger object takes longer to fill. Below
30 GB the target stays at 1,850,000,000 and objects keep the loader's default
row groups.

On a 4 GB machine the budget is smaller than the objects need, so the loader
flushes early to stay inside it and the objects come out smaller, about 17 MB
median. `--max-flush-delay 30s` lets an object fill before the age trigger
closes it. Every value can be overridden from the environment (`RAVEL_BATCH_ROWS`,
`RAVEL_TARGET_BYTES`, `RAVEL_PIPELINE_DEPTH`, `RAVEL_READ_CURSORS`,
`RAVEL_LOAD_MEMORY_BYTES`, `RAVEL_MAX_FLUSH_DELAY`, `RAVEL_GROUP_TARGET_BLOCKS`;
an empty `RAVEL_GROUP_TARGET_BLOCKS` keeps the loader's default). **There is no post-load
step**: no compaction, no catalog fold, no VACUUM equivalent, so the layout the
queries run against is the layout ingest produced.

Before the load, `./load` sets two tenant settings that decide how ingest lays
rows out. `bloom-scope set --scope text` keeps bloom filters to text columns
(log bodies and severity); `hits` has none, so no column is covered and each
block keeps only the minimum filter. No statement here has a predicate a bloom
filter would answer. `clustering-key
set --column EventDate --column UserID --bucket-width 1d` sorts the rows inside
each object by counter, day, `EventDate`, `UserID` and time, the order
ClickHouse's own entry gives its table with `PRIMARY KEY (CounterID, EventDate,
UserID, EventTime, WatchID)`; the counter is already Ravel's stream, so it is
not repeated. Sorted columns compress better and the bloom section shrinks
to its minimum: on c6a.4xlarge with v0.27.0 the two settings together took the stored
data from 10.3 GB to 8.3 GB and the load from about 900 s to about 640 s, with
the same answers.

`./data-size` reports the tenant's whole durable footprint in the bucket (data
objects, commit records, manifests, catalog snapshots), which is where all of
Ravel's state lives.

### What the cold figures measure here

The reference machine's disk is a 500 GB gp2 volume. Ravel holds no data on
local disk, so a cold run (server restarted, page cache dropped) fetches what it
needs from the store, and the store reads it from that volume. Since 0.24.0, a
server whose store is on loopback defaults its fetch policy to `latency-first`,
which reads only the byte ranges a statement needs from each object instead of
whole objects; `server.log` names it with `policy_source="default-loopback"`.
On c6a.4xlarge, in this repository's fresh-VM setup, with RustFS as the store,
the cold sum over the 43 statements was 365.7 s on v0.26.0, against 486.6 s on
v0.23.0 and 1,291.0 s on v0.21.0. With s3s-fs as the store it was 163.1 s on
v0.27.0 with 24 MB objects, 117.7 s with the 46 MB one-group objects the
30 GB tier writes, and 108.0 s with those objects sorted by the clustering key
and without bloom filters (`results/20261026`). On v0.28.0 with the 8 GB
decoded cache, the entry as it stands, it was 106.2 s cold, and the hot sum
(the faster of the second and third tries) fell from 50.2 s to 37.9 s
(`results/20261030`). The dataset is 8.3 GB. The RustFS results stay under
their own dates.

A warm run is served from the read cache or from the store. Since 0.24.0, a
server whose store is on loopback gives its fetch cache 24% of its memory
budget: 7.0 GB on this machine. Since 0.28.0 the decoded cache sits on top of
it, so a warm statement on this machine also skips decoding the columns it
already decoded.

### The tuned configuration

This directory publishes one result, the stock one. A tuned run belongs in its
own top-level entry the way the other tuned entries in this repository do, and
that is left for a follow-up. The tuned configuration is server flags passed
through `RAVEL_TUNED_ARGS` in `./start`:

```
RAVEL_TUNED_ARGS="--logs-fetch-policy latency-first --fetch-concurrency 256 --sql-max-query-bytes <stock value>" ./benchmark.sh
```

From 0.24.0 on, a loopback store already defaults to `latency-first`, so on
this harness only the last two flags differ from a stock start. The
description and figures in the rest of this section were measured on v0.23.0.

`latency-first` is a named policy, not a tuning constant: it says spend
requests to save wall time, and resolves the byte quantities exactly as
`byte-minimal` does, so a logs read takes ranged reads wherever they save
bytes. It only pays off once fetch concurrency is raised with it, which is what
the second flag does (it sets the object-store GET permits, the SQL partition
count and the PromQL fan-out together). Raising the permits shrinks the derived
per-query pool, so the third flag holds it at the value a stock start logs on
its `sql_max_query_bytes` line (about 14.2 GB on c6a.4xlarge); without it the
widest `GROUP BY` (q33) is refused.

Measured on v0.23.0 against RustFS on c6a.4xlarge, the tuned configuration
took the cold sum from 486.6 s to 384.6 s and left the hot sum unchanged
(56.9 s and 57.1 s). It is not safe on smaller machines. In-flight fetches at
256 permits draw on the same process memory budget the queries do, so on
c6a.2xlarge (16 GB) three statements are refused that the stock configuration
answers, and more on 8 and 4 GB.

### Reference: the same binaries on real S3

Measured by us on c6a.4xlarge against a fresh S3 bucket in the instance's
region (us-east-1), credentials from the instance role, with the same driver
and the same true-cold protocol, on the released v0.23.0 binaries and this
entry's `./load` and `./start` unchanged except for the credential source
(`--s3-auth instance-role`). One pass. Not reproducible by this harness, which
does not run entries on real S3, and therefore not a results file. Cold is the
sum of the first runs; hot is the sum of the better of the second and third
runs.

| configuration | load | cold | hot | hot geomean | statements |
|---|---|---|---|---|---|
| stock, real S3, v0.23.0 | 932 s | 186 s | 63 s | 1.01 s | 43 of 43 |
| stock, local RustFS, v0.23.0 | 924 s | 487 s | 57 s | 0.74 s | 43 of 43 |

Cold is faster on S3 because nothing waits on the 250 MB/s gp2 volume: S3
serves the ranged reads in parallel at network speed. Hot is slightly slower
because the larger fetch cache share a loopback store gets does not apply to
a remote endpoint: the derived cache was 7.5 GB on this machine, below the
10.2 GB dataset, so part of each warm run goes back to S3.

The earlier reference, v0.16.1 with ~4 MB objects, measured a 483 s cold and
430 s hot sum on real S3, with q33 refused.

## Notes

- Queries go over the HTTP SQL endpoint on loopback, one process per query, the
  same shape as the other daemon entries.
- Ravel is a telemetry database rather than a general-purpose warehouse: the
  `hits` columns are modelled as typed attribute columns on log records, and
  every query states a time window covering the dataset because the SQL
  endpoint's window defaults to the last hour.
- The heaviest whole-table aggregates can exceed the derived per-query memory
  pool on a small instance and are reported as errors rather than being run
  with a raised limit. q33 reserves about 10.9 GB. It completes on c6a.4xlarge
  and larger; on instances with less memory it can still be refused.
- q28 averages `octet_length("URL")`. ClickHouse's `length()` counts bytes and
  DataFusion's counts characters, so `octet_length` is the faithful
  translation; q29 still uses `length("Referer")`.
